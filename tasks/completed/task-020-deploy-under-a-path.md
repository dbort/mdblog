# task-020: Deploy a vault under a path of a larger Cloudflare site

## Summary
A new guide explains how to publish a vault at a path such as `example.com/notes/` on a domain whose other pages come from a separate Worker, and how the root page can show the vault's recent posts. Cloudflare's Git builds republish the site on every push to the vault repo. To make the guide work as written, mdblog gains a `routes` setting for the site's Worker, a `timezone` setting for dates written without an offset, an `mdblog deploy` command that builds, uploads and checks the site in one step, and a short script the vault copies so that Cloudflare's deploy command is one line.

## Must Have
- [x] `[worker]` in `_site/mdblog.toml` accepts an optional `routes` key: a non-empty array of non-empty strings. `load_config` raises `ConfigError` naming `mdblog.toml` when `routes` is not an array, is empty, or holds a non-string or empty string, and the existing unknown-key error still fires for any other key.
- [x] With `routes` set, the `wrangler.json` that `mdblog stage` writes holds `routes` with the patterns in their given order and `"workers_dev": false`. Without `routes`, it is identical to what stage writes today, so `test_wrangler_config_serves_the_assets_as_the_worker` passes unchanged.
- [x] `mdblog deploy VAULT` stages the vault into a temporary directory outside the vault, runs the pinned wrangler as `deploy --config <bundle>/wrangler.json` with `WRANGLER_ENV` applied, and then checks the deployed site at its `base_url` with the checks `mdblog verify` makes. It exits 0 only when all of them pass.
- [x] `mdblog deploy` exits 1 without running wrangler when the build fails, when `[worker]` is missing (the error names `mdblog.toml` and `[worker]`), or when wrangler is not installed (the message is `find_wrangler`'s).
- [x] When wrangler exits nonzero, `mdblog deploy` exits 1, reports wrangler's status, and makes no verify request.
- [x] When verification still fails after `mdblog deploy`'s bounded retries, it exits 1 and its message says the upload succeeded, so the failing site is live.
- [x] `mdblog deploy` leaves no temporary directory behind, on success or on any failure above.
- [x] Tests cover every Must Have above with a fake wrangler executable and a fake HTTP server, and none contacts Cloudflare.
- [x] `_site/mdblog.toml` accepts an optional top-level `timezone`: an IANA zone name such as `America/New_York`. `load_config` raises `ConfigError` naming `mdblog.toml` when it is not a string or names no known zone.
- [x] With `timezone` set, every command (`build`, `check`, `serve`, `stage`, `deploy`) reads a `date` datetime with no offset in that zone, with the offset in force on that date (a January date and a July date in `America/New_York` get `-05:00` and `-04:00`), and judges "in the future" and "today" by the current time in that zone, whatever the machine's local zone. A draft's modification-time fallback is shown in that zone too. Without `timezone`, behavior is unchanged and the existing local-zone tests pass as written.
- [x] `templates/deploy.sh` holds a commit placeholder and mdblog's clone URL. Run as `sh _site/deploy.sh` from a vault's root, it clones mdblog into a new temporary directory, checks out the commit, and runs that checkout's `tools/workers-build` on the vault.
- [x] `tools/workers-build VAULT` installs pixi at the version its `PIXI_VERSION` names when none is on `PATH`, installs wrangler with `npm ci` in its own checkout, and runs `mdblog deploy` on `VAULT` through `pixi run --locked`. With any other number of arguments, it exits 2 with a usage line.
- [x] `tools/check` runs shellcheck on every shell script in the repo (`tools/check`, `tools/manual-qa`, `tools/workers-build`, `templates/deploy.sh`), and each passes.
- [x] The guide `docs/deploy-under-a-path.md` exists, and `grep -i dbort docs/deploy-under-a-path.md` prints nothing. Its Workers Builds deploy command is `sh _site/deploy.sh`, and it holds no `curl` or `TZ=`. The root page's recent-posts script sits under its own subheading, beside recommendations for styling the entries.
- [x] `README.md` § Commands documents `mdblog deploy` and links the guide. In `docs/vault-format.md`, § Properties gives `timezone`'s effect on `date`. In § Site folder, the `_site/mdblog.toml` row states the rules for `routes` and `timezone`, and a row for `_site/deploy.sh` links the guide.
- [x] `tools/check` exits 0.

## Advice
- **Publisher (user decision):** Cloudflare Workers Builds connected to the vault repo runs every publish: its deploy command runs the vault's `_site/deploy.sh`, which ends in `mdblog deploy`. GitHub Actions is out of scope, so there is no workflow template and no actionlint or zizmor step. Workers Builds keeps the deploy credentials in Cloudflare, where the author already deploys the root site. The author can also run `mdblog deploy` locally to publish by hand.
- **Trigger (user decision):** every push to the vault repo's production branch publishes. The roadmap warns that an automatic trigger puts a half-finished edit to a published note live; the author accepts that. The guide says it, and notes that an Obsidian Git setup that pushes automatically publishes on each automatic push.
- **mdblog source (user decision):** the build clones mdblog's public GitHub repo and checks out a full commit SHA that the vault's `_site/deploy.sh` holds. The author makes the repo public; the task does not. A pin in the vault means bumping mdblog is a commit, which also triggers a rebuild, while editing a dashboard setting triggers nothing. mdblog itself never reads the file. Clone mdblog outside the vault checkout, because mdblog reads every `.md` outside `_site/`, and mdblog's own docs would fail the build.
- **Deploy scripts (user decision, 2026-11-09):** the vault holds a copy of `templates/deploy.sh` as a small bootstrap: the pinned commit, mdblog's clone URL, clone, checkout, `exec` mdblog's `tools/workers-build`. `tools/workers-build` holds the setup steps and the pixi version, so they change with the pinned mdblog and the vault copy rarely changes. The template names mdblog's real clone URL, so it works as copied; only the guide must stay free of `dbort`. Both stay linear POSIX `sh` (`CLAUDE.md` § Scripts stay simple), so the Cloudflare image's `sh` runs them. Clone into `mktemp -d`, never a fixed path, so a rerun cannot collide. `tools/workers-build` makes `VAULT` absolute before calling pixi, because `--manifest-path` does not set the working directory the vault path resolves against. Set the pixi install script's telemetry opt-out, as `WRANGLER_ENV` opts wrangler out. The scripts get no tests: each failure is loud (a failed clone, a failed install, `mdblog deploy`'s own exit), and only a real Cloudflare build exercises them.
- **Timezone (user decision, 2026-11-09):** `timezone` in `mdblog.toml` replaces the guide's inline `TZ`, so a vault builds the same on any machine. It is optional and falls back to the machine's local zone, which keeps existing vaults and tests unchanged. It applies to every command, so `serve` previews what `deploy` publishes. Validate it with `zoneinfo.ZoneInfo`; conda-forge's `tzdata` reaches the pixi environment as a dependency of Python, so add no dependency. Thread it from the loaded config through `convert_vault` into `select_notes` and the date helpers in `properties.py` and `publish.py`, and convert `now` into the zone there, so callers that inject `now` keep working.
- **Routes (user decision):** they live in the vault's `[worker]` table, beside the Worker name, because this repo holds nothing site-specific. Pass each pattern through as a string and let wrangler resolve the zone; `/work` confirms against wrangler's docs that string routes need no zone field. `"workers_dev": false` comes only with routes: Hugo writes `base_url` into every link, so a copy on `workers.dev` would link away from itself and duplicate the site. Do not cross-check routes against `base_url`; a mismatch fails loudly at deploy's verify step.
- **Domain sharing:** Cloudflare gives a route precedence over a Custom Domain on the same hostname ([Routes](https://developers.cloudflare.com/workers/configuration/routing/routes/), [Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)), so the root Worker keeps its Custom Domain or `/*` route and the vault's Worker claims `example.com/notes/*`. A request for `/notes` with no trailing slash reaches only the root Worker, so the guide has the root site redirect it, with a `_redirects` entry in a static-assets root or its equivalent. Domain-wide files such as `robots.txt` belong to the root site: crawlers ignore `/notes/robots.txt`, and the root's `robots.txt` governs `/notes/`.
- **Recent posts on the root page (user decision):** the guide gives a short inline script, under its own subheading (user decision, 2026-11-09), that fetches `<base>/recent.json` and renders each item's title link, date and summary. It names `src/mdblog/theme/layouts/home.recent.json` as the contract and restates no field rule beyond the key names the script uses. The script is untested by decision. It builds its DOM with `textContent` and attributes, never `innerHTML`, because titles and summaries come from notes. It checks `response.ok` and catches failures, so a missing file leaves the list empty without an unhandled rejection. Give the elements class names, and add short recommendations for styling the entries (user decision, 2026-11-09): style through those classes in the root site's own CSS, format the date for readers, and keep summaries short.
- **Acceptance (user decision):** ship on review, with no manual-QA check. Each Cloudflare-specific instruction in the guide (Workers Builds build and deploy commands, the token Workers Builds provides to the deploy step, how a Worker gets connected for its first build, the `_redirects` syntax) is confirmed against Cloudflare's current docs during `/work`, because nothing in `tools/check` can test them and the author follows the guide only after `/ship`. If the docs leave a step uncertain, ask the author rather than guess.
- **Deploy command shape:** reuse `stage_site`, `find_wrangler` and `WRANGLER_ENV` from `stage.py`, and `verify.py`'s checks. Take wrangler as an injectable `Sequence[str]`, like `serve_bundle`, so tests pass a fake. Credentials come from wrangler's own environment (`CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, or a local `wrangler login`); mdblog never reads or prints them. Retry verification for at most a named constant's worth of time, because a fresh upload can take a moment to reach every Cloudflare location; `mdblog verify` itself keeps making one request per check. No rollback: the guide says how to roll back in Cloudflare instead.
- **Out of scope:** preview deployments, custom headers, and a site at a domain root. All stay in M5. The guide describes production only.
- **Guide content:** frugal and generic (`CLAUDE.md` § Writing style by destination). Use two example repos, a root site (a `wrangler.toml` plus an assets directory) and a vault (`_site/mdblog.toml`, `_site/deploy.sh`), with `example.com` and `/notes/` as placeholders. Point to `vault-format.md` for config rules and to code for tunable values. Cover: the two-Worker layout and why it works; the vault's `base_url`, `timezone`, `[worker] name` and `routes`; copying and pinning `_site/deploy.sh`; the root site's redirect, domain-wide files, and its recent-posts script and styling under their own subheading; the Workers Builds settings (empty build command, `sh _site/deploy.sh` as the deploy command, preview builds off); publishing by hand; what a failed build leaves live (nothing changes) versus a failed verify (the new site is live); and bumping mdblog. Use one dashboard label consistently for the Worker's build settings, and drop the `www` sentence (round 1 notes).
- **Standing obligations:** *strict static checks* apply to the config, stage, deploy and timezone code, and to the shell scripts, which shellcheck checks inside `tools/check` (add `shellcheck` from conda-forge to `pixi.toml`). *Scripts stay simple*: `templates/deploy.sh` and `tools/workers-build` are linear shell, and any logic goes in `mdblog deploy`. *Docs point to code*: each doc step below names the facts it adds. *Test where the risk is*: unit tests cover each config rule and each deploy branch with fakes. No test runs a real `wrangler deploy`, because `tools/check` stays local. Give the existing real-wrangler `stage --serve` test's vault a `routes` key, so the one real-tool run also shows `wrangler dev` accepts the generated config.
- **Cloudflare findings (2026-11-09, `/work`):** Cloudflare's docs leave open whether the build and deploy commands share `PATH` and files, whether build variables reach the deploy command, and where the deploy command runs. The guide therefore leaves the build command empty and runs every step from the deploy command, `tools/workers-build` calls pixi by its absolute path after installing it, and the zone comes from `mdblog.toml`. Workers Builds overrides the config's Worker name with `WRANGLER_CI_OVERRIDE_NAME` ([Troubleshooting](https://developers.cloudflare.com/workers/ci-cd/builds/troubleshoot/)), which reaches wrangler because `upload` passes the environment through. Its auto-created token has Workers Scripts (edit) and Workers Routes (edit) on every zone ([Configuration](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/)). Preview builds run `npx wrangler preview` against a config the vault lacks, so the guide has them turned off ([Build branches](https://developers.cloudflare.com/workers/ci-cd/builds/build-branches/)).
